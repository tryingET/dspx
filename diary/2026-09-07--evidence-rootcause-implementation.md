Copying staged-addition bytes then left them untracked, allowing actual `prek run

Implemented in the existing Git/preparation/process seam:
- Full-local-custody **v3** requires `index: {sha256, entries}`: exact original raw
  index SHA256 plus canonical NUL-terminated UTF-8 stage-list records. V1/V2 manifests
  reject; existing independent pytest node/collector baselines remain mandatory.
- Read-only binary admission supports SHA1 index v2, stage0, regular/executable/link
  modes and no semantic flags. Live source links still reject; deleted historical
  links retain tombstones. Optional TREE cache is discarded before Git reads it;
  other extensions, split/sparse/resolve-undo/fsmonitor, assume-valid, skip-worktree,
  intent-to-add, unmerged, malformed paths/modes/OIDs/checksums and missing/nonblob
  staged objects fail closed. This is an intentionally restricted feature contract,
  not general Git-index compatibility.
- Config-free views validate staged blob types and pack those objects (including
  unreachable staged additions) into the new private clone. Bounded immutable stdin
  is fed from private temporary storage and SHA256-receipted. Private `read-tree
  --empty` / `update-index -z --index-info` restores exact reviewed stage0 entries.
  No `git add` of copied files, source-index/object writes, external Git/filter/hook
  configuration, lazy fetch or worktree checkout is used by this preparation seam.
- HEAD, dirty tracked/unstaged bytes, intentional deletions and untracked identities
  remain independently checked. Original raw-index changes (even stat-cache-only)
  fail admission/copy/stages; private index bytes are stable across copy and every
  computational stage. Membership joins the receipt's source identity.
